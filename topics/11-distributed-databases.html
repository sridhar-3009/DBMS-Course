Topic 11

Distributed Databases

Raft consensus, two-phase commit, consistent hashing, and sharding strategies — how Google Spanner and CockroachDB provide ACID at global scale.

Spanner (Google)CockroachDBYugabyteDB VitessTiDB
Core Concepts
🗳

Raft Consensus

Leader-based consensus for replicated logs. Leader handles all writes, replicates to followers. Majority quorum required for commit. Automatic leader election on failure.

✂️

Sharding

Partition data across multiple nodes by a shard key. Range sharding (ordered keys) vs Hash sharding (uniform distribution). Each shard independently handles its key range.

🔁

Replication

Synchronous: wait for N replicas to confirm before commit (strong consistency, higher latency). Asynchronous: commit immediately, replicate in background (low latency, risk of data loss on primary failure).

⚖️

Two-Phase Commit (2PC)

Coordinator asks all participants to PREPARE. If all say YES, coordinator sends COMMIT to all. Used for distributed transactions spanning multiple shards. Blocking on coordinator failure.

How It Works

Raft Leader Election

1

Heartbeats

The Leader sends periodic heartbeat AppendEntries RPCs to all followers to prevent election timeouts. Followers reset their election timer on each heartbeat received.

2

Election Timeout

If a follower doesn't receive a heartbeat within a random timeout (150–300ms), it assumes the leader is dead. It increments its term, transitions to Candidate, votes for itself.

3

RequestVote

The Candidate sends RequestVote RPCs to all other nodes. A node grants its vote if: it hasn't voted in this term, and the candidate's log is at least as up-to-date as its own.

4

Majority Quorum

If the Candidate receives votes from a majority (⌊n/2⌋ + 1 of n nodes), it becomes the new Leader. For 3 nodes: need 2 votes. For 5 nodes: need 3 votes.

5

Log Replication

New Leader sends AppendEntries with the pending log entry. Once a majority acknowledges, the entry is committed. Leader notifies followers of the commit in the next heartbeat.

Range Sharding

  • Keys sorted — great for range queries
  • Risk: hot spot on sequential keys (auto-increment PKs)
  • CockroachDB, TiDB, HBase
  • Easy range scans within a shard
  • Uneven load if key distribution is skewed

Hash Sharding

  • Uniform distribution across shards
  • Range queries require scatter-gather
  • Cassandra (consistent hashing), Vitess
  • No hot spots on sequential inserts
  • Resharding requires remapping keys
Anti-patterns

⚠ Using auto-increment PKs as shard keys

Sequential keys → all writes go to the last range shard → hot spot. One node gets 100% of write traffic. Use random UUIDs (UUID v4) or time-bucketed keys (ULID/KSUID) for uniform distribution.

⚠ Cross-shard transactions for every operation

2PC is expensive: 2 round trips, blocking on coordinator failure. Design your shard key so that related data lives on the same shard (tenant_id, user_id) — keep transactions local where possible.

⚠ Under-sized Raft groups

A 2-node cluster has no fault tolerance — one node failure loses quorum. Always use odd numbers: 3 (tolerate 1 failure), 5 (tolerate 2). More than 7 nodes in a Raft group hurts write latency due to larger quorum.

Interview Q&A
How does the Raft consensus algorithm ensure linearizability?▾
Raft ensures linearizability (the strongest single-object consistency model) through: (1) Leader completeness: a leader always has all committed log entries. Votes are only granted to candidates whose log is at least as up-to-date. (2) Majority commit: an entry is committed only after being replicated to a majority of nodes — even if the leader crashes, at least one node in any future majority quorum has the entry. (3) State machine safety: all nodes apply log entries in order. (4) Read linearizability: the leader must confirm its leadership before serving reads (via a "read index" or heartbeat round-trip) — otherwise a partitioned stale leader could serve stale reads. CockroachDB uses leader leases to serve reads without a round trip.
What is the difference between synchronous and asynchronous replication?▾
Synchronous: before ACKing a write, wait for at least one (or more) replicas to confirm they've written the data. Zero RPO (Recovery Point Objective) — no committed data lost on primary failure. Tradeoff: write latency includes replica round-trip. Used by Raft (majority quorum), PostgreSQL synchronous_standby_names. Asynchronous: ACK the write immediately after writing to primary only. Replicas catch up in the background. Lower write latency but RPO > 0 — failover to an async replica may lose recently committed transactions. MySQL binlog replication is async by default. PostgreSQL streaming replication is async by default. Rule of thumb: use synchronous for primary data, async for read replicas where slight staleness is acceptable.
Explain database sharding and how you choose a shard key.▾
Sharding splits a table horizontally across multiple database instances. Each shard holds a subset of rows based on the shard key. Shard key selection criteria: (1) High cardinality: enough distinct values to distribute evenly. (2) Low update frequency: changing shard key requires moving the row. (3) Query alignment: most queries filter on the shard key — avoiding cross-shard scatter-gather. (4) No hot spots: avoid monotonically increasing values (auto-increment IDs) — use UUID v4, hash(user_id), or time-bucketed IDs. Good shard keys: user_id (for user-centric apps), tenant_id (for SaaS), geographic region. Bad: created_at alone (all writes go to latest shard), status (low cardinality).
How does Google Spanner achieve global ACID transactions?▾
Spanner combines several innovations: (1) TrueTime API: GPS + atomic clocks in every data center. TrueTime returns a time interval [earliest, latest] with bounded uncertainty (~7ms). Commit timestamps are chosen to be after the TrueTime interval's latest bound — ensuring external consistency (if Txn2 starts after Txn1 commits, Txn2's commit timestamp > Txn1's). (2) Paxos groups: each data shard is a Paxos group (similar to Raft) for strong consistency. (3) 2PC + Paxos: distributed transactions use 2PC for cross-shard atomicity, with each shard's state replicated via Paxos. (4) MVCC: Spanner uses multi-version storage and TrueTime for consistent snapshots across all shards globally. RPO=0, RTO~seconds for regional failures.
What is Vitess and when would you use it?▾
Vitess is a horizontal sharding system for MySQL — originally built at YouTube, now used by GitHub, Slack, and others. It sits in front of MySQL instances and handles: query routing (rewrite SQL to target the correct shard), connection pooling (reduces MySQL connection overhead from thousands to hundreds), online schema changes (pt-osc style without blocking), cross-shard queries (scatter-gather), resharding with minimal downtime, and failover. Use Vitess when: your MySQL database is growing beyond what a single instance can handle (writes > ~5K/sec, storage > a few TB), you want to stay on MySQL (operational familiarity), and you need horizontal write scalability. If you're greenfield and need global scale, consider CockroachDB or YugabyteDB instead.
