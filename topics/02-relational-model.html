Topic 02

The Relational Model

Codd's formal foundation: relations, tuples, keys, constraints, and the relational algebra that powers every SQL query under the hood.

PostgreSQLMySQLOracle SQL ServerSQLite
Core Concepts
📋

Relation (Table)

A relation is a set of tuples (rows), all sharing the same schema (ordered list of attribute names and domains). Order of tuples is undefined — it's a set, not a list.

🔑

Keys

Superkey → minimal superkey = Candidate Key → chosen CK = Primary Key. Foreign Keys enforce referential integrity between relations.

🔗

Referential Integrity

A FK value must either be NULL or match a PK in the referenced table. ON DELETE CASCADE / SET NULL / RESTRICT control what happens when the parent row is deleted.

🧮

Relational Algebra

Six fundamental operations: σ (select rows), π (project columns), ⋈ (join), ∪ (union), − (difference), × (Cartesian product). All SQL compiles down to these.

How It Works

From Algebra to SQL

1

σ — Selection (WHERE)

Filters rows based on a predicate. σ salary>80000 (employees) — equivalent to WHERE salary > 80000. Only filters rows, never reduces columns.

2

π — Projection (SELECT cols)

Keeps only specified columns, removes duplicates. π name,dept (employees) — the SQL SELECT DISTINCT name, dept.

3

⋈ — Natural Join

Combines two relations on all common attribute names, eliminating duplicates. SQL's NATURAL JOIN. More common: theta-join with explicit predicate (the SQL JOIN … ON).

4

Set Operations (UNION, INTERSECT, EXCEPT)

Combine result sets. Relations must be union-compatible (same arity, compatible domains). UNION ALL skips deduplication for performance.

Relational Algebra → SQL
-- Relational algebra: π name,dept_name (σ salary>80k (employees ⋈ departments))
SELECT   e.name, d.dept_name
FROM     employees e
JOIN     departments d ON e.dept_id = d.dept_id
WHERE    e.salary > 80000;

-- Key constraints in DDL
CREATE TABLE orders (
  order_id   INT     PRIMARY KEY,
  customer_id INT    NOT NULL REFERENCES customers(customer_id) ON DELETE CASCADE,
  total      NUMERIC(10,2) CHECK (total >= 0)
);

Key Insight: INNER vs OUTER Joins

INNER JOIN returns only matched rows. LEFT JOIN keeps all left rows (unmatched right = NULL). RIGHT JOIN keeps all right rows. FULL OUTER JOIN keeps all rows from both sides. In practice, LEFT JOIN is far more common than RIGHT JOIN (rewrite by swapping table order).

Anti-patterns

⚠ Choosing the wrong join type

Using INNER JOIN when you need LEFT JOIN silently drops rows. Always verify expected result cardinality. A missing row in the result is often worse than an error.

⚠ Missing referential integrity constraints

Storing FK values without declaring FOREIGN KEY lets orphaned rows accumulate — child rows pointing to deleted parents. This causes silent data corruption that's expensive to fix later.

⚠ Using natural joins in production queries

NATURAL JOIN matches on ALL common column names. Adding a column to a table can silently change join semantics. Always use explicit ON conditions.

Interview Q&A
What is the difference between a superkey, candidate key, and primary key?▾
A superkey is any set of attributes that uniquely identifies a tuple. A candidate key is a minimal superkey — no proper subset is also a superkey. A primary key is the one candidate key chosen by the designer as the principal identifier. Example: in a users table, {user_id}, {email}, and {user_id, email} are all superkeys. {user_id} and {email} are candidate keys (both minimal). The designer picks {user_id} as the PK.
Explain referential integrity and ON DELETE options.▾
Referential integrity means every non-null FK value must exist as a PK in the referenced table. When the parent row is deleted: ON DELETE CASCADE — delete all child rows automatically (useful for orders→items). ON DELETE SET NULL — set the FK to NULL (useful for optional relationships). ON DELETE RESTRICT / NO ACTION — reject the delete if child rows exist (safest default). ON DELETE SET DEFAULT — set to a default value. Choose based on the business rule: is a child row meaningful without its parent?
What is the difference between INNER JOIN and CROSS JOIN?▾
A CROSS JOIN is the Cartesian product — every row in table A combined with every row in table B. If A has 1,000 rows and B has 1,000 rows, the result has 1,000,000 rows. No ON clause. An INNER JOIN is a cross join plus a filter: only tuples where the join predicate is true survive. CROSS JOINs are rarely intentional in production and often indicate a missing ON clause. They're useful for generating test data or calendar tables.
What does relational algebra's closure property mean?▾
Closure means every relational algebra operation takes one or more relations as input and produces a relation as output. This is powerful because it enables composition: you can nest operations arbitrarily, using the output of one operation as input to the next. SQL exploits this: subqueries, CTEs, and derived tables all rely on closure. Every SQL query produces a "virtual table" (result set) that can be treated as a relation for further querying.
Why does SQL use DISTINCT? Doesn't the relational model already eliminate duplicates?▾
Strictly, yes — a relation is a set, so no duplicate tuples are allowed. But SQL is based on bags (multisets), not sets, for performance: eliminating duplicates requires sorting or hashing, which is expensive. So SELECT without DISTINCT can return duplicates. SELECT DISTINCT adds the deduplication step. This is a deliberate SQL deviation from pure relational theory — the tradeoff is performance over theoretical purity. For aggregations, duplicates are often intentional (you want to count all rows, not just unique ones).
