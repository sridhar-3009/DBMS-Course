Topic 06

Database Indexing

B+trees, covering indexes, composite key ordering, index selectivity — everything you need to turn 10-second queries into 10-millisecond queries.

PostgreSQL GiST/GINMySQL InnoDB B+tree Redis Sorted SetElasticsearchMongoDB
Core Concepts
🌲

B+Tree Index

Balanced tree with all data in leaf nodes. Internal nodes store keys for navigation. O(log n) search, O(log n) insert/delete. Leaf nodes linked for range scans.

🎯

Clustered vs Non-Clustered

Clustered: row data stored in B+tree leaf pages (InnoDB PK). One per table. Non-clustered: leaf pages store (key, PK pointer). Multiple allowed. Extra hop to data page.

🛡

Covering Index

Index contains all columns needed by a query — no "back to table" heap/clustered lookup needed. The index IS the query result. Massively reduces I/O.

📏

Index Selectivity

Ratio of distinct values to total rows. High selectivity (e.g., user_id) → index worth using. Low selectivity (e.g., boolean) → full scan may be faster.

How It Works

B+Tree Mechanics

1

Tree Structure

Root node → internal nodes (navigation keys only) → leaf nodes (keys + row pointers or data). All data in leaves. Height typically 3–4 for tables of millions of rows.

2

Point Query (exact match)

Start at root. At each internal node, follow the child pointer where search_key falls in the key range. Reach leaf in O(height) = O(log n) comparisons.

3

Range Query

Find the leaf containing the range start key. Then follow the linked-list of leaf nodes to the right until the range end is exceeded. I/O is proportional to result size, not table size.

4

Index Maintenance

Every INSERT/UPDATE/DELETE must update all affected indexes. Indexes speed reads but slow writes. Each additional index is a tax on write throughput — only add what's needed.

5

Composite Index Key Order

Index on (a, b, c) supports queries on (a), (a,b), (a,b,c) but NOT on (b) or (c) alone. The leftmost prefix rule: columns must be used left-to-right for the index to be usable.

SQL — Index Creation
-- Composite index: column order matters!
-- For: WHERE dept='Engineering' AND hire_date > '2020-01-01'
CREATE INDEX idx_emp_dept_hire ON employees (dept, hire_date);

-- Covering index: includes salary so no heap lookup needed
-- For: SELECT salary WHERE dept='Eng' ORDER BY hire_date
CREATE INDEX idx_emp_covering ON employees (dept, hire_date) INCLUDE (salary);

-- Partial index: only index active users (PostgreSQL)
CREATE INDEX idx_active_users ON users (email)
  WHERE status = 'active';

-- Hash index: O(1) equality only, no range support
CREATE INDEX idx_hash_email ON users USING HASH (email);

-- Verify index usage
EXPLAIN (ANALYZE, BUFFERS)
  SELECT * FROM employees WHERE dept = 'Engineering';

Index Bloat and Maintenance

Over time, B+trees can develop bloat from deletions (pages that are half-empty but not compacted). PostgreSQL's VACUUM and MySQL's OPTIMIZE TABLE rebuild indexes. Monitor index bloat with pg_stat_user_indexes and pg_relation_size. Unused indexes waste write performance — use pg_stat_user_indexes.idx_scan = 0 to find them.

Anti-patterns

⚠ Indexing low-selectivity columns

An index on a boolean column (true/false) with 50/50 distribution is rarely used — the planner will choose a full scan. Partial indexes on the rare value are effective: CREATE INDEX WHERE is_deleted = true.

⚠ Functions on indexed columns in WHERE

WHERE LOWER(email) = 'alice@…' — the index on email is NOT used. Use a function-based index: CREATE INDEX ON users (LOWER(email)). Or store the normalized value in a separate column.

⚠ Over-indexing write-heavy tables

Each index on a table costs an extra B+tree update on every INSERT/UPDATE/DELETE. A table with 15 indexes can have 10× slower write throughput than an unindexed one. Index only what queries actually need.

⚠ Wrong column order in composite index

Index on (status, created_at) serves queries filtering by status. Index on (created_at, status) serves range queries on created_at. Reversing these makes one query do a full scan. Lead with the equality column, follow with the range column.

Interview Q&A
What is the difference between a clustered and non-clustered index?▾
A clustered index determines the physical order of rows on disk — the B+tree leaf pages ARE the data pages. In InnoDB (MySQL), the primary key is always the clustered index. There can be only one per table. Accessing via PK is extremely efficient — the data is right there. A non-clustered index is a separate B+tree whose leaf pages store (indexed column, PK) pairs. To fetch row data, you first look up the index (getting the PK), then do a second lookup in the clustered index. This second lookup is called a "key lookup" or "heap fetch." Covering indexes avoid this second hop.
When should you NOT create an index?▾
Don't index when: (1) The table is small (< a few thousand rows) — full scans are fast and the optimizer may choose them anyway. (2) The column has very low cardinality (gender, boolean) — the optimizer won't use it for most queries. (3) The column is write-heavy and rarely queried — each index costs a write on every DML operation. (4) The column is already part of a composite index as a prefix — a separate single-column index may be redundant. (5) The column is frequently updated — index maintenance overhead is high. Always validate with EXPLAIN before and after; index decisions are empirical.
Explain composite index column ordering with an example.▾
Index on (dept, hire_date): useful for WHERE dept = 'Eng' (equality on first col), WHERE dept = 'Eng' AND hire_date > '2020' (equality + range), and ORDER BY dept, hire_date. NOT useful for WHERE hire_date > '2020' alone — the index sorts first by dept, then by hire_date within each dept, so you can't skip to hire_date. Rule: put equality columns first, range columns last. If a query has both WHERE dept = ? and ORDER BY hire_date, put dept first. The index supports filtering AND sorting without an extra sort step.
What is index selectivity and how does it affect query planning?▾
Index selectivity = (number of distinct values) / (total rows). Selectivity of 1.0 is perfect (every value unique, like a UUID PK). Selectivity of 0.5 means 50% of rows have the same value. The query planner uses statistics (pg_statistic) to estimate how many rows a condition will match. High selectivity → index lookup returns few rows → worth the index overhead. Low selectivity → index returns ~50% of rows → full scan cheaper (sequential I/O beats random I/O for large fractions). Threshold is roughly: use index if < 5–10% of rows selected; full scan otherwise. Partial indexes can create high-selectivity sub-indexes for specific values.
What are GiST and GIN indexes in PostgreSQL?▾
GiST (Generalized Search Tree): a framework for building balanced tree indexes for non-standard data types. Used for: geometric types (PostGIS point/polygon intersection), range types, full-text search (tsvector), network addresses. Supports: overlaps, contains, nearby operators. GIN (Generalized Inverted Index): an inverted index — maps element values to the rows containing them. Used for: full-text search (best performer), JSONB containment (@>), arrays (&&). GIN is larger and slower to build than GiST but faster to query for multi-element containment. Use GIN for text search and JSONB; GiST for geometric and range queries.
