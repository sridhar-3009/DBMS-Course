Topic 08

Concurrency Control

Two-phase locking, MVCC, deadlock detection, and optimistic vs pessimistic strategies — how databases handle thousands of simultaneous transactions correctly.

PostgreSQL MVCCInnoDB 2PL OracleCockroachDB SSIMySQL
Core Concepts
🔐

Two-Phase Locking (2PL)

Growing phase: acquire locks, never release. Shrinking phase: release locks, never acquire. Guarantees serializability. Strict 2PL holds all locks until commit.

📸

MVCC

Each write creates a new row version. Readers see a consistent snapshot without locking. Readers never block writers, writers never block readers. PostgreSQL's primary concurrency strategy.

💀

Deadlock

T1 waits for T2's lock. T2 waits for T1's lock. Cycle. Neither can proceed. DBMS detects via wait-for graph cycle detection, kills one transaction to break the cycle.

⚖️

Optimistic Concurrency

No locking. Execute freely, validate at commit. If conflict detected, abort and retry. Efficient under low contention; expensive under high contention (wasted work).

How It Works

1

Shared Lock (S)

Acquired by READ operations. Multiple transactions can hold S locks simultaneously on the same row. An S lock request is blocked only if an X lock is held.

2

Exclusive Lock (X)

Acquired by WRITE operations. Only one transaction can hold an X lock. Blocks all other S and X requests. In Strict 2PL, X locks are held until COMMIT.

3

Deadlock Detection

Build a wait-for graph: nodes = transactions, edges = "T1 waits for lock held by T2". Cycle = deadlock. Victim selection: kill the transaction with the fewest locks / least work done (to minimize wasted effort).

4

Deadlock Prevention

Wound-Wait: older T aborts younger T that holds a needed lock (wound). Wait-Die: older T waits; younger T dies instead of waiting. Both prevent cycles at the cost of extra aborts.

SQL — Locking
-- Explicit row lock: SELECT FOR UPDATE
BEGIN;
  SELECT * FROM accounts WHERE id = 42 FOR UPDATE;
  -- Row 42 is now X-locked. Other transactions block here.
  UPDATE accounts SET balance = balance - 100 WHERE id = 42;
COMMIT;

-- Skip locked rows (non-blocking queue processing)
SELECT * FROM jobs
WHERE  status = 'pending'
LIMIT  1
FOR UPDATE SKIP LOCKED;

-- Advisory locks for application-level mutual exclusion
SELECT pg_advisory_xact_lock(12345);
-- Lock released automatically on COMMIT/ROLLBACK

Anti-patterns

⚠ Acquiring locks in inconsistent order

If T1 locks table A then B, and T2 locks table B then A, a deadlock is guaranteed under concurrent execution. Always acquire locks in a consistent global order (e.g., alphabetical by table name, or by PK ascending).

⚠ Table-level locks for row-level operations

Using LOCK TABLE when a row-level FOR UPDATE would suffice blocks the entire table. All concurrent readers and writers queue up. Row-level locking has far higher concurrency.

⚠ Not handling deadlock errors in application code

Deadlocks are normal in concurrent applications. The DBMS will abort one transaction with a "deadlock detected" error (SQLSTATE 40P01 in PostgreSQL). Application code must catch this and retry the transaction — not crash.

Interview Q&A
Explain 2PL and why it guarantees serializability.▾
Two-Phase Locking divides a transaction's lifetime into two phases: (1) Growing phase: locks are acquired, none released. (2) Shrinking phase: locks are released, none acquired. The lock point is the moment the first lock is released. The key insight: you can serialize transactions by their lock points. Because no transaction can acquire new locks after releasing old ones, any conflicting pair of transactions has a well-defined serial order (the one whose lock point comes first "wins"). Strict 2PL (used by most databases) holds all locks until COMMIT, eliminating cascading aborts and dirty reads. The tradeoff: more contention but simpler correctness reasoning.
How does deadlock detection work and how do you prevent deadlocks in application code?▾
Detection: the DBMS maintains a wait-for graph. Nodes are transactions; a directed edge T1→T2 means T1 is waiting for a lock held by T2. A cycle in this graph = deadlock. The DBMS periodically runs cycle detection (DFS) and picks a victim to rollback — typically the youngest transaction or the one with fewest locks. Prevention in application code: (1) Consistent lock ordering: always lock resources in the same order (e.g., by ascending PK) — eliminates the cycle precondition. (2) Short transactions: hold locks briefly to reduce overlap windows. (3) Retry on deadlock error: catch SQLSTATE 40P01, retry with exponential backoff. (4) Avoid user input mid-transaction: never wait for external I/O while holding locks.
What is the difference between optimistic and pessimistic concurrency control?▾
Pessimistic: assume conflicts will happen, prevent them upfront with locks. Acquire locks before accessing data; no conflict possible during execution; release on commit. Best under high contention. Optimistic: assume conflicts are rare. Execute without locks; at commit, validate that no conflict occurred (check if any read row was modified by a concurrent committed transaction). If conflict → abort and retry. Best under low contention. Implementations: SELECT FOR UPDATE is pessimistic; version-column optimistic locking (UPDATE … WHERE version = :v, fail if 0 rows updated) is optimistic. MVCC snapshot isolation is a form of optimistic concurrency — reads are free, commits validate for serialization conflicts.
What is SELECT FOR UPDATE SKIP LOCKED and when would you use it?▾
SELECT … FOR UPDATE SKIP LOCKED acquires an exclusive lock on selected rows but skips (doesn't block on) rows already locked by other transactions. Use case: job queues. Multiple workers each do SELECT * FROM jobs WHERE status='pending' LIMIT 1 FOR UPDATE SKIP LOCKED — each worker gets a different job without blocking each other. Without SKIP LOCKED, all workers would queue up on the same first row, creating a thundering herd. Alternative patterns: use message queues (Redis, RabbitMQ) instead of DB tables for high-throughput job processing. DB-based queues work well up to ~1K jobs/sec.
What is Serializable Snapshot Isolation (SSI)?▾
SSI (used in PostgreSQL's SERIALIZABLE level and CockroachDB) provides true serializability with MVCC performance. It tracks read-write dependencies: if transaction T2 reads data that T1 has written, and T1 reads data that T2 has written (a read-write cycle), one must be aborted. SSI uses "predicate locks" (tracking which ranges were read) to detect these dangerous cycles at commit time rather than at lock acquisition time. Benefit over 2PL: readers never block; much higher read concurrency. Cost: some transactions abort at commit (false positives in cycle detection). PostgreSQL's implementation has near-zero overhead under low conflict workloads, making it the recommended default isolation level.
