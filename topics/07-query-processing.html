Topic 07

Query Processing

From SQL string to query execution plan — parsing, optimization, join algorithms, and how the DBMS picks the cheapest strategy using statistics.

PostgreSQLMySQLSQL Server BigQueryPresto

At a Glance

  • Query pipeline: Parse -> Validate -> Rewrite -> Optimize -> Execute.
  • Cost-based optimizer uses table statistics (row count, data distribution, index cardinality) to compare plans.
  • Nested loop join: O(n*m), fast when inner table has an index. Hash join: O(n+m), best for large un-indexed joins.
  • Sort-merge join: efficient when both sides are already sorted or have matching indexes.
  • EXPLAIN ANALYZE shows actual vs estimated rows — large discrepancies indicate stale statistics.
Core Concepts

Query Optimizer

Enumerates possible execution plans, estimates cost (I/O + CPU) using table statistics, and selects the minimum-cost plan. Cost-based optimizers use histograms and distinct value counts.

Join Algorithms

Nested Loop (small inner table), Hash Join (one side fits in memory), Merge Join (both sides sorted). The optimizer picks based on table sizes and available indexes.

Statistics & Cardinality

Histograms track value distribution. Cardinality estimates predict how many rows survive filters. Bad estimates → bad plans → slow queries. ANALYZE refreshes statistics.

Materialized Views

Precomputed query results stored on disk. Trade stale data for instant reads. Used for expensive aggregations, complex joins, and BI dashboards.

How It Works

Query Lifecycle

1

Parse

SQL text → parse tree. Validates syntax and checks table/column names exist. Resolves aliases. Semantic analysis checks types and permissions.

2

Rewrite (Rule System)

Apply rewrite rules: expand views, apply row-level security policies, push down predicates into subqueries. PostgreSQL's rule system transforms the parse tree before planning.

3

Plan (Optimize)

Generate candidate plans using dynamic programming. For each plan node, estimate cost = (I/O cost × pages) + (CPU cost × rows). Select the minimum-cost complete plan.

4

Execute

Walk the plan tree (iterator/volcano model). Each node calls GetNext() on its children. Rows flow upward through the tree. Sort and Aggregate nodes may buffer all input before producing output.

PostgreSQL EXPLAIN
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT d.dept_name, COUNT(*), AVG(e.salary)
FROM  employees e JOIN departments d ON e.dept_id = d.dept_id
WHERE e.hire_date > '2020-01-01'
GROUP BY d.dept_name;

Hash Join

  • Build hash table from smaller relation
  • Probe with larger relation rows
  • O(n+m) time, O(min(n,m)) space
  • Best when one side fits in memory
  • Unsorted output

Merge Join

  • Both inputs must be sorted on join key
  • Walk both sorted lists in lockstep
  • O(n log n + m log m) if sorting needed
  • Best with sorted inputs or sort already needed
  • Produces sorted output
Anti-patterns

Stale statistics causing bad plans

If ANALYZE hasn't run after a large data load, the optimizer uses outdated row count estimates. A table that grew from 100K to 10M rows without ANALYZE may get Nested Loop joins instead of Hash joins — orders of magnitude slower.

Implicit type casts defeating index usage

WHERE user_id = '12345' when user_id is BIGINT forces a cast on every row during a sequential scan. The optimizer can't use an index because it doesn't know the cast will preserve order.

Not using EXPLAIN ANALYZE before deploying

EXPLAIN (without ANALYZE) shows only estimated costs. EXPLAIN ANALYZE shows actual row counts and time. A query with estimated 100 rows but actual 100,000 rows has bad statistics and will have a bad plan.

Interview Q&A
What is the Volcano/Iterator model of query execution?▾
The Volcano model (also called iterator model) implements query execution as a tree of operators, each implementing a GetNext() interface. The top-level operator (Result) calls GetNext() on its child, which calls GetNext() on its child, and so on. Data flows upward one tuple at a time. Benefits: memory-efficient (one tuple in flight per operator), composable, simple to implement new operators. Drawback: poor CPU cache utilization due to virtual function calls and branching. Modern databases (Snowflake, DuckDB) use vectorized execution: process batches of 1024 rows at once using SIMD, dramatically improving cache efficiency and throughput.
How does the query optimizer handle join ordering for 3+ tables?▾
With n tables, there are n!/2 possible join orderings (left-deep trees). For n=4 that's 12; for n=10 that's 1.8M. The optimizer uses dynamic programming (as in System R / PostgreSQL): start with single-table costs, then for each pair, triple, etc. find the cheapest plan using the previously computed sub-plans. PostgreSQL uses this up to 8 tables, then switches to a genetic algorithm (GEQO) for larger queries. Heuristics: push filters early (reduce cardinality fast), join on equality predicates before inequality, prefer smaller-to-larger ordering.
What is predicate pushdown and why is it important?▾
Predicate pushdown moves WHERE conditions as early as possible in the query plan — ideally into the table scan. Instead of: join 1M employees × 200 departments, then filter for dept='Engineering', the optimizer pushes the filter into the employees scan first — reducing the input to the join from 1M to ~50K rows. The join is 20× smaller. In distributed systems (Spark, BigQuery), predicate pushdown to the storage layer (e.g., Parquet column pruning) can avoid reading irrelevant files entirely — reducing I/O by orders of magnitude.
What is a query plan hint and when should you use one?▾
Plan hints let you override the optimizer's choice: force an index (USE INDEX in MySQL), join order, or join type. They should be a last resort — used only when: (1) you've confirmed with EXPLAIN ANALYZE that the optimizer chose a bad plan, (2) you've refreshed statistics and it still makes the wrong choice, (3) you understand exactly why the optimizer is wrong. Hints are brittle: they survive schema changes silently (the hint may force a plan that becomes even worse after a new index is added). Prefer fixing statistics, adding/removing indexes, or rewriting the query. PostgreSQL doesn't support hints natively (use pg_hint_plan extension); MySQL does.
When should you use a materialized view?▾
Use a materialized view when: (1) A complex query (multi-table join + aggregation) is run frequently and reads take seconds. (2) The underlying data changes infrequently enough that stale reads are acceptable. (3) You need to index the result of a query (not possible with regular views). Refresh strategies: REFRESH MATERIALIZED VIEW CONCURRENTLY (PostgreSQL — doesn't lock reads), scheduled job, or on-demand. Trade-off: write amplification (every base table update may trigger a refresh) vs read speed. Alternatives: Redis/Memcached cache, denormalized summary tables updated by triggers, or incremental view maintenance (supported in some OLAP systems).
