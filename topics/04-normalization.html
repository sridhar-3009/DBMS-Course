Topic 04

Database Normalization

Eliminate redundancy and update anomalies by decomposing tables through functional dependency analysis — 1NF through BCNF, animated step by step.

MySQLPostgreSQLOracle SQL Server
Core Concepts

Functional Dependency

A → B means knowing A's value uniquely determines B's value. E.g., student_id → student_name. The foundation of all normal forms.

1NF — Atomic Values

All attribute values must be atomic (indivisible). No multi-valued attributes (comma-separated lists), no repeating groups, each row uniquely identifiable.

2NF — No Partial Dependencies

Every non-key attribute must depend on the WHOLE primary key. Applies when PK is composite. Split tables so each non-key column depends on the full PK.

3NF / BCNF — No Transitive Deps

No non-key attribute should depend on another non-key attribute. BCNF is stricter: every functional dependency X→Y must have X as a superkey.

How It Works

Step-by-Step Normalization

1

Identify Functional Dependencies

List all FDs: which attribute(s) uniquely determine others? E.g., {order_id, product_id} → quantity, but order_id → customer_name (partial dep if PK is composite).

2

Check 1NF — Atomicity

Replace multi-value cells (e.g., "Apple, Banana") with separate rows. Remove repeating column groups (item1, item2, item3 → normalize to item rows). Each cell = one value.

3

Check 2NF — Full Key Dependency

With composite PK, identify which non-key columns depend on only part of the key. Extract those into a new table with the partial key as PK. Original table keeps the rest.

4

Check 3NF — Transitive Dependencies

Find non-key → non-key chains: zip → city → state. Extract city/state into a separate zip_codes table with zip as PK. Only store zip in the original table.

5

BCNF — Stronger Form

For every FD X→Y, X must be a superkey. 3NF allows Y to be a prime attribute (part of a candidate key); BCNF does not. Most tables in 3NF are also in BCNF.

SQL — 3NF Decomposition
-- Denormalized: order_data(order_id, customer_name, customer_city, product, price)
-- FDs: order_id → customer_name, customer_city
--      customer_city → customer_state  (transitive via city!)
--      (order_id, product) → price

-- After 3NF normalization:
CREATE TABLE customers (
  customer_id  SERIAL PRIMARY KEY,
  name         VARCHAR(100),
  zip_code     CHAR(5) REFERENCES zip_codes(zip)
);
CREATE TABLE zip_codes (
  zip          CHAR(5) PRIMARY KEY,
  city         VARCHAR(100),
  state        CHAR(2)
);
CREATE TABLE orders (
  order_id     SERIAL PRIMARY KEY,
  customer_id  INT REFERENCES customers
);
CREATE TABLE order_items (
  order_id     INT REFERENCES orders,
  product      VARCHAR(100),
  price        NUMERIC(10,2),
  PRIMARY KEY  (order_id, product)
);

At a Glance

  • 1NF: atomic values, no repeating groups. Every cell holds a single value.
  • 2NF: no partial dependency — non-key columns depend on the whole primary key (only matters with composite keys).
  • 3NF: no transitive dependency — non-key columns depend only on the key, not on other non-key columns.
  • BCNF: stricter than 3NF — every determinant is a candidate key. Eliminates all anomalies.
  • Denormalization is a deliberate performance trade-off, not a mistake — but start normalized.

When to Denormalize

Normalization is right for OLTP (transactional) workloads. OLAP / reporting workloads often benefit from star/snowflake schemas with controlled denormalization — fewer JOINs mean faster analytical queries. Always profile first; never denormalize without a measured performance problem.

Anti-patterns

Storing comma-separated values in a single column

tags = "sql,database,postgres" violates 1NF. Can't index individual values, can't enforce FK constraints, string parsing in queries is error-prone and slow.

Denormalizing "for performance" without profiling first

Redundancy creates update anomalies: update customer's city in 10,000 order rows vs 1 customer row. The JOIN is usually fast enough; the update anomaly is always costly.

Over-normalizing OLAP schemas

Pushing to 6NF in reporting databases means dozens of JOINs per analytical query. Snowflake schemas over-normalized hurt BI tool performance. Dimension tables are intentionally denormalized in star schemas.

Interview Q&A
What are the three types of update anomalies in a denormalized table?▾
Insert anomaly: can't insert a fact without inserting an unrelated fact. E.g., can't add a new department to the order table without also having an order. Update anomaly: the same fact stored redundantly in multiple rows — update customer city in one row and it's inconsistent with others. Delete anomaly: deleting a row destroys unrelated information. E.g., deleting the last order for a customer deletes the customer's address too. Normalization solves all three by storing each fact exactly once.
Explain the difference between 3NF and BCNF with an example.▾
3NF allows a non-key attribute to determine a prime attribute (one that's part of a candidate key). BCNF does not — every determinant must be a superkey. Example: a relation R(student, course, teacher) where each teacher teaches one course ({teacher} → {course}) and {student, course} is a CK. The FD teacher→course violates BCNF (teacher is not a superkey) but satisfies 3NF (course is a prime attribute). BCNF decomposition: split into (teacher, course) and (student, teacher). Tradeoff: BCNF decomposition may not preserve all functional dependencies; 3NF always does.
When would you intentionally denormalize and how do you manage the risks?▾
Denormalize when: (1) profiling shows JOIN cost is the bottleneck (rare for OLTP). (2) Read-heavy OLAP workloads where update anomalies are tolerable. (3) Caching computed aggregates (e.g., order_count on users table — update via trigger or background job). Management strategies: use database triggers to keep denormalized data in sync; use materialized views; do batch reconciliation jobs; document the denormalization contract clearly. Never denormalize based on intuition — always measure.
What is Armstrong's Axioms and why are they important?▾
Armstrong's Axioms are a sound and complete set of inference rules for deriving all functional dependencies from a given set: (1) Reflexivity: if B ⊆ A then A→B (trivial FD). (2) Augmentation: if A→B then AC→BC. (3) Transitivity: if A→B and B→C then A→C. Derived rules: Union (if A→B and A→C then A→BC), Decomposition, and Pseudo-transitivity. They're important for computing closure of attributes (F+) — used to find all candidate keys and verify normal forms algorithmically.
What is a lossless-join decomposition and why does it matter?▾
A decomposition of relation R into R1 and R2 is lossless if R1 ⋈ R2 = R — no spurious tuples are introduced by the join. If the decomposition is lossy, you can't reconstruct the original data, which means information is destroyed. Condition: R1 ∩ R2 must be a superkey of either R1 or R2. All normal form decompositions (to 3NF, BCNF) should be lossless-join. The related property — dependency preservation — ensures all FDs are enforceable in at least one decomposed table. BCNF may sacrifice dependency preservation but never lossless-join.
