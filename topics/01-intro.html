Topic 01

Introduction to DBMS

Why file systems fail at scale — and how a Database Management System solves data independence, integrity, concurrency, and recovery.

MySQLPostgreSQLSQLite Oracle DBMariaDBIBM Db2
Core Concepts
🗂

Data Independence

Physical independence: change storage without touching app logic. Logical independence: restructure schema without rewriting queries.

🔒

ACID Properties

Atomicity, Consistency, Isolation, Durability — the four guarantees that make transactions reliable in multi-user environments.

🏗

Three-Schema Architecture

External (views), Conceptual (logical schema), Internal (physical storage) — three levels of abstraction that isolate users from hardware.

👥

Concurrency Control

Multiple users reading and writing simultaneously without corrupting data. The DBMS serializes conflicting operations transparently.

How It Works

DBMS Architecture

1

Query Parser

The SQL string is tokenized, syntax-checked, and parsed into a parse tree. Semantic checks validate table names, column types, and user permissions.

2

Query Optimizer

The optimizer generates multiple execution plans, estimates costs using statistics (row counts, data distribution), and selects the cheapest plan.

3

Execution Engine

The physical plan is executed. The engine calls Storage Manager to fetch pages from the Buffer Pool (RAM cache backed by disk I/O).

4

Transaction Manager

Wraps each query in a transaction context. Acquires locks, writes WAL (Write-Ahead Log) before dirty pages, releases locks on commit/rollback.

5

Recovery Manager

On crash, replays WAL from the last checkpoint (redo phase), then undoes any uncommitted transactions (undo phase) to restore a consistent state.

SQL
-- Simple DBMS anatomy: one statement, many internal steps
SELECT e.name, d.dept_name
FROM   employees e
JOIN   departments d ON e.dept_id = d.dept_id
WHERE  e.salary > 80000
ORDER BY e.name;

-- Internally:
-- 1. Parse → AST
-- 2. Optimize → choose SeqScan vs IndexScan, pick join algorithm
-- 3. Execute → fetch pages from buffer pool
-- 4. Lock rows (shared lock on READ in REPEATABLE READ+)
-- 5. Return result set

Anti-patterns

⚠ Using flat files instead of a DBMS

CSV files have no atomicity, no query language, no concurrent access control, and no recovery. Fine for scripts; catastrophic for production data.

⚠ Ignoring normalization from day one

Denormalized schemas feel easy initially but create update anomalies, data redundancy, and painful migrations as the application grows.

⚠ Treating the DBMS as a dumb storage layer

Not using constraints (FK, NOT NULL, CHECK) shifts validation to application code — the worst of both worlds and much harder to enforce consistently.

Interview Q&A

Common Interview Questions

What is the difference between a DBMS and a file system?▾
A file system provides raw byte storage organized in files and directories — no query language, no constraints, no transactions, no concurrent access control. A DBMS adds: a data model (relational, document, etc.), a declarative query language (SQL), integrity constraints (FK, NOT NULL), ACID transactions, concurrent multi-user access with locking/MVCC, and crash recovery via Write-Ahead Logging. Use a file system for blobs and configuration; use a DBMS for structured, transactional data.
Explain the three-schema architecture.▾
The three-schema architecture separates concerns into three levels: (1) External schema — user views, each showing a subset of the data tailored to a role (e.g., HR sees salaries, developers see user IDs). (2) Conceptual schema — the global logical description of all tables, relationships, and constraints, independent of storage. (3) Internal schema — the physical storage details: file organization, index structures, page sizes, compression. The mappings between levels enable independence: you can change disk layout without altering the logical schema, and vice versa.
What are the four ACID properties? Give a real-world example of each.▾
Atomicity: A bank transfer deducts $100 from Account A and credits Account B — if the credit fails, the debit is rolled back. No partial state. Consistency: A foreign key constraint ensures you can never have an order referencing a non-existent customer. The DB moves from one valid state to another. Isolation: Two users booking the last seat on a flight don't both succeed — the second sees the updated, post-first-booking state. Durability: After a COMMIT returns, the transaction survives a power failure. The WAL ensures committed data is flushed to durable storage.
What is data independence and why does it matter?▾
Data independence means application code doesn't need to change when the storage or schema changes. Physical independence: you can switch from a heap file to a clustered B+tree index without modifying any SQL. The optimizer adapts. Logical independence: you can add a column or split a table into two (and provide a view) without breaking existing queries. This matters because storage decisions and schema evolution happen frequently; coupling them to application code creates a maintenance nightmare.
What is the role of a DBA in a production system?▾
A Database Administrator (DBA) is responsible for: schema design and evolution (DDL migrations), performance tuning (index selection, query optimization, buffer pool sizing), backup and recovery planning (RPO/RTO targets, WAL archiving, PITR), security (user roles, column-level encryption, audit logging), capacity planning (storage growth, replication lag), and high-availability setup (primary/replica, failover). In cloud-native environments the DBA role increasingly overlaps with SRE and data engineering.
