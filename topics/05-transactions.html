Topic 05

Transactions & ACID

How databases guarantee correctness in the face of crashes, concurrent users, and hardware failures — and what happens when each guarantee is weakened.

InnoDB (MySQL)PostgreSQL CockroachDBSpannerOracle

At a Glance

  • Isolation levels (weakest to strongest): READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE.
  • Dirty read: reading an uncommitted change. Prevented at READ COMMITTED+.
  • Non-repeatable read: same SELECT returns different rows. Prevented at REPEATABLE READ+.
  • Phantom read: new rows appear in a repeated range query. Prevented at SERIALIZABLE.
  • MVCC: readers don't block writers — each transaction sees a consistent snapshot.
Core Concepts

Atomicity

All-or-nothing. A transaction either commits fully or rolls back completely — no partial state ever visible. Enforced via WAL undo log.

Consistency

A transaction takes the DB from one valid state to another. Schema constraints, triggers, and application invariants must all hold before and after.

Isolation

Concurrent transactions don't interfere. The illusion: each transaction executes as if it were the only one running. Enforced via locking or MVCC.

Durability

Once committed, data survives crashes. WAL (Write-Ahead Log) ensures committed changes are written to durable storage before the commit returns.

*PostgreSQL's REPEATABLE READ also prevents phantom reads via MVCC snapshot isolation.

1

Dirty Read

T1 reads data written by T2 that hasn't committed yet. If T2 rolls back, T1 read data that never existed. Only occurs at READ UNCOMMITTED.

2

Non-Repeatable Read

T1 reads a row. T2 commits an UPDATE to that row. T1 reads the same row again and gets a different value. Prevented at REPEATABLE READ+.

3

Phantom Read

T1 executes a range query. T2 INSERTs a row matching the range and commits. T1 re-runs the same query and gets different (extra) rows. Prevented at SERIALIZABLE.

4

Lost Update

T1 and T2 both read balance=100, both compute balance+50, both write 150. One write overwrites the other. Net effect: only one of the two updates is reflected.

SQL — Transaction Control
-- Basic transaction
BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

-- Set isolation level for a single transaction
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
  SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;  -- pessimistic lock
  UPDATE accounts SET balance = balance - 50 WHERE id = 1;
COMMIT;

-- Savepoints for partial rollback
BEGIN;
  INSERT INTO orders ... ;
  SAVEPOINT after_order;
  INSERT INTO payments ... ;
  ROLLBACK TO after_order;  -- undo payment only
COMMIT;

Anti-patterns

Long-running transactions

Transactions held open for seconds or minutes block other writers, accumulate MVCC versions (bloating the database), and increase the blast radius of failures. Keep transactions short and focused.

Doing HTTP calls inside a transaction

If the HTTP request hangs, your transaction holds locks indefinitely. Never call external services inside BEGIN…COMMIT. Prepare data, commit, then make the call.

Using READ UNCOMMITTED outside of monitoring queries

READ UNCOMMITTED is almost never the right choice in application code. The only legitimate use case is approximate analytics dashboards where dirty reads are acceptable.

Interview Q&A
How does MVCC (Multi-Version Concurrency Control) work in PostgreSQL?▾
PostgreSQL's MVCC stores multiple versions of each row. Every row has hidden system columns: xmin (transaction ID that created this version) and xmax (transaction ID that deleted/updated it, or 0 if still current). When you read, PostgreSQL's "snapshot" includes a list of in-progress transactions. A row version is visible to your snapshot if xmin committed before your snapshot AND (xmax is 0 or xmax hasn't committed yet). Writers create a new row version and set xmax on the old one — they never overwrite. This means readers never block writers and writers never block readers. VACUUM periodically reclaims dead row versions (xmax committed).
What is a dirty read, and when can it actually be useful?▾
A dirty read is when transaction T1 reads data written by T2 that hasn't committed yet. If T2 rolls back, T1 read data that never "officially" existed — a phantom fact. In most application code, this is never acceptable. Legitimate uses: approximate reporting dashboards (you want the freshest in-progress data for a live counter), monitoring queries where stale reads for 1–2 seconds are acceptable, and debugging (seeing exactly what an in-progress transaction is doing). In PostgreSQL, even READ UNCOMMITTED gives you READ COMMITTED behavior — the engine won't show truly dirty reads. SQL Server and MySQL support it.
What is the difference between COMMIT and ROLLBACK?▾
COMMIT makes all changes in the transaction permanent and visible to other transactions. The DBMS flushes WAL to durable storage before returning success (durability guarantee). Locks are released. ROLLBACK undoes all changes made in the transaction — the database state is as if the transaction never happened. The WAL undo log is applied to reverse changes. Locks are released. Implicit rollback happens on session disconnect, crash, or explicit error handling. SAVEPOINT allows partial rollback within a transaction without aborting the whole thing.
Explain the lost update problem and how SELECT FOR UPDATE solves it.▾
Lost update: T1 reads balance=100, T2 reads balance=100, T1 writes 150 (100+50), T2 writes 150 (100+50) — one update is lost (should be 200). SELECT FOR UPDATE acquires an exclusive row lock at read time. T2's SELECT FOR UPDATE blocks until T1 commits, then T2 reads the updated value 150 and writes 200 correctly. Alternatives: (1) Atomic UPDATE: UPDATE … SET balance = balance + 50 — the DBMS serializes concurrent updates atomically. (2) Optimistic locking with version columns: read version=5, update WHERE version=5, fail if another transaction already updated. Choose based on contention level.
What is a savepoint and when would you use it?▾
A savepoint marks a point within a transaction to which you can roll back without aborting the entire transaction. SQL: SAVEPOINT name, ROLLBACK TO name, RELEASE name. Use cases: (1) Bulk import with partial error tolerance: insert batch, if a row fails ROLLBACK TO savepoint, skip that row, continue. (2) Complex multi-step workflows where early steps should survive even if later steps fail. (3) Testing: wrap test code in a transaction, use savepoints to reset state between sub-tests, rollback the outer transaction at the end. Note: savepoints are not a substitute for good error handling design.
